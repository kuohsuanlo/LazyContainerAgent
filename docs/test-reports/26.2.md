# LazyContainerAgent 測試報告 — Paper 26.2

**結論：✅ PASS（實機測試）。** 在真實 Paper 26.2 / Java 25 上，agent（在 JVM 啟動時掛進伺服器、動態改寫類別的那支程式）注入成功，容器資料經過 lazy 載入（延遲載入：箱子裡的物品先不解析成物件，等真的要讀取時才解） + raw 回寫（原封回寫：把當初讀進來的原始位元組原樣寫回磁碟，不重新打包） + 重載後完全保留（含 data-component：1.20.5 之後 Minecraft 用來描述物品屬性，例如耐久、附魔的新資料格式），shadow（影子模式：照常跑原版存檔，同時在旁邊另外算一份 agent 版本的結果來比對，不動到實際資料）下逐位元組（一個 byte 一個 byte 比）與 vanilla（原版：沒被 agent 改動、Minecraft 原本的行為）完全相同（`shadowMismatch=0`）。

## 建置
- 把 `template/LazyContainerTemplate.java` 這個範本檔對著 **26.2 mojmap NMS** 重新編譯（JDK 25）。NMS＝net.minecraft.server，Minecraft 伺服器內部的核心程式碼；mojmap＝用 Mojang 官方命名對照過、看得懂名字的那份版本。編出來的 classfile（.class 位元碼檔）= **major69**（class 檔的版本號，這裡對應 Java 25）；agent 本身的類別 = major65（對應 release 21，也就是 Java 21，但一樣能在 Java 25 的 server 上跑）。
- ASM 9.10.1（操作 Java 位元碼 bytecode、在類別載入當下改寫它的函式庫）經過 relocate（把套件路徑改名搬位，避免和伺服器裡別的 ASM 版本撞名衝突；共 107 個 `…/lazycontainer/asm/` 類別）。
- **這些 NMS 方法/欄位的簽章（名稱與參數型別）對 26.2 完全相容、不用改任何一行源碼**：`ContainerHelper.loadAllItems/saveAllItems`、`TagValueInput.input`（public 欄位）/`createGlobal`、`TagValueOutput.buildResult/createWithContext`（`TagValueInput`/`TagValueOutput` 是 NMS 把方塊資料讀成、寫成 NBT 的類別；NBT＝Minecraft 儲存方塊/物品資料用的二進位格式）、`getItems/getContents/setItems/getContainerSize`、`MinecraftServer.registryAccess()` — 範本（template）編譯零錯誤。

[LazyContainer] transformed leaf net/minecraft/world/level/block/entity/ShulkerBoxBlockEntity

- 成功把範本的欄位/方法 splice（接枝：把外來的欄位和方法插進既有類別）進 `BaseContainerBlockEntity`（NMS 裡所有容器方塊的共同父類別；BlockEntity＝方塊實體，附在方塊上、替它存額外資料的物件，例如箱子的內容物）；Chest / ShulkerBox / Barrel 三個 leaf（繼承自父類別、最底層的實際子類別）全部 transformed（改寫完成）。
- 掃描三份 boot log，`VerifyError / IllegalAccessError / NoSuchMethod/Field / NoClassDefFound / IncompatibleClassChange / base not spliced / skip leaf` 這些錯誤/失敗訊號的出現次數 = **全部 0**（代表 JVM 驗證器 — JVM 載入類別時檢查位元碼合不合法的機制 — 接受把 major69 的 template 嫁接進 26.2 NMS）。

## 測試 2 — 資料完整性 3-boot round-trip（決定性）
程序（`run-test.sh`）：BOOT1 放箱+存 → BOOT2 磁碟 lazy 載入 + 未碰即 raw 回寫 → BOOT3 讀回比對。
- 放入：`chest{Items:[diamond×42, diamond_sword{components:{damage:10}}, netherite_ingot×7]}`
- BOOT3 讀回：
```
[{Slot:0b, count:42, id:"minecraft:diamond"},
 {Slot:5b, count:1, components:{"minecraft:damage":10}, id:"minecraft:diamond_sword"},
 {Slot:9b, count:7, id:"minecraft:netherite_ingot"}]
```
- **物品 id、count、data-component(`damage:10`)全保留。**
- 各 boot 計數：
  | boot | stash | rawSave | ensure | eagerLoad | shadowMismatch | benignReorder |
  |---|---|---|---|---|---|---|
  | 1（放箱+存）| 5 | 7 | 0 | 0 | **0** | 0 |
  | 2（lazy 載入+raw 回寫）| 1 | 1 | 0 | 0 | **0** | 0 |
  | 3（讀回）| 1 | 2 | 0 | 0 | **0** | 0 |
- `stash>0`＝lazy 載入生效；`rawSave>0`＝raw 回寫生效；`shadowMismatch=0`＝raw 回寫與 vanilla encode 逐位元組相同 → **✅ PASS**。

## 測試 3 — shadow 真實世界（demo-server）
在含真實世界資料的 demo-server（Paper 26.2）以 `-Dlazycontainer.shadow=true` 開機：
```
[LazyContainer] stash=56 ensure=0 rawSave=56 eagerLoad=0 shadowMismatch=0 benignReorder=0 (SHADOW) active=true
[LazyContainer] shutdown stats: stash=56 ... rawSave=56 ... shadowMismatch=0 benignReorder=0
```
- **56 個真實容器**走 lazy raw-writeback，全程 + 關機時 `shadowMismatch=0` → 在真實資料上 raw 回寫與 vanilla 逐位元組相同。

## 覆蓋與限制
- 已驗：注入正確性、跨重啟資料完整性（含 component）、真實世界 shadow byte-identical。
- 未在本報告涵蓋：26.2 的效能 benchmark（1.21.11 的 spark 數據見 [`../spark/SUMMARY.md`](../spark/SUMMARY.md)；26.2 機制相同，效益等價，待正式節點 spark 量測）。
- ensure（decode-on-access）路徑在 headless 測試未觸發（無玩家/漏斗互動，`ensure=0`）；其正確性由 round-trip 的讀回比對與 shadow 間接覆蓋。

## 上線建議
照原 v1.0 流程：第一次以 `-Dlazycontainer.shadow=true -Dlazycontainer.verbose=true` 開機，跑數天確認 `shadowMismatch=0` 後再移除 shadow 取效能。回退＝移除 `-javaagent` 旗標重啟（磁碟格式從未改變，無資料遷移）。
